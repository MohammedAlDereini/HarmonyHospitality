Assumptions

Stated so they can be challenged. Each is marked where it changes a decision.

  1. Users. Hotel staff on desktop browsers (front desk, reservations, cashiers, managers, night auditors) are the primary audience. Housekeeping and engineering may use tablets later. Guests never use this app.
  2. Browsers. Current and previous major versions of Chrome, Edge, Firefox and Safari. No Internet Explorer, no legacy Edge.
  3. Screens. 1366×768 at 100 % and 125 % zoom is the smallest desk screen; 1920×1080 is common. These match the prototype's proven viewports.
  4. Sessions. Staff keep the app open for a full shift (8–12 hours), often with several tabs.
  5. Network. Hotel LAN or Wi-Fi, typically under 100 ms to the region; occasional drops. Not designed for offline operation (see 1.10).
  6. Same-origin deployment. The BFF serves the Angular files and proxies the APIs on one origin, so the browser talks to one host only. This is what RFC 10017 §6.1 describes and what WebBffSettings already assumes.
  7. Languages. Arabic and English at launch; more later. Arabic is right-to-left.
  8. Money. Several currencies per tenant country (SAR, JOD, AED…). JOD has three minor units; amounts must never be handled as binary floating point.
  9. Time. Every property has one IANA time zone and its own business date, changed by night audit, not by midnight.
  10. Team. One product team at the start; the same people build backend and frontend.

What changes for the frontend compared with today's React app

No token code at all in the browser: no sessionStorage tokens, no refresh logic, no reading claims from a JWT. Sign-in is a full-page navigation to /bff/login; everything the UI needs about the person comes from /bff/session.

1.4 Standalone components, routing and lazy loading

  • ANGULAR Standalone components only (no NgModules). Zoneless change detection is the default since v21 ("Zoneless is the default in Angular v21+").
  • The property is in the URL. /p/:property/front-office/hotel-now, /p/:property/rooms/plan, /admin/… for platform administration. A deep link opens the same property in any tab; two tabs can work two properties without fighting over a global setting.
  • One lazy boundary per domain (loadChildren), and loadComponent per heavy page. Domain routes declare their own providers (stores, adapters) so they are created when the route activates and destroyed when it leaves.
  • Guards check usability, not security. canMatch with the access service hides routes the person cannot use and the entitlement the property lacks; the backend still refuses on its own (section 3).
  • Preloading: a custom strategy that preloads only routes in the person's dock and favourites, after the first idle period, never on metered connections.
  • @defer for below-the-fold and rarely opened widgets (charts, help, history panels).

Invalidation

  1. After my own mutation: the adapter returns the new version of the entity; the store patches it in place and marks dependent queries stale (for example, check-in → arrival row, room status, folio balance, "Hotel now" counts).
  2. After someone else's change: a real-time event names entity, version and property; if the version is newer, the store refetches that entity or marks the list stale. Events for another property are dropped.
  3. After a gap: if the per-property sequence number jumps, or the connection was down, the store refetches everything it shows (resync) instead of trusting partial events.
  4. On property switch or sign-out: every property-scoped cache is cleared; nothing from the previous property can render under the new name (the prototype's honesty rule).

Cross-domain workflows

A workflow that spans domains (check-in touches reservations, rooms, cashiering and key encoding) lives in the feature of the domain that owns the user's intent (front-office/feature-check-in). It calls each domain's public data-access API in order, carries one idempotency key per step, and shows each step's outcome. The backend should eventually offer one command for check-in; until then the client orchestrates and must handle partial completion (section 1.11).

RECOMMENDATION No global store library at the start. Angular's resources and signals cover the needs above. @ngrx/signals 22.0 is the first candidate if a store grows beyond a few hundred lines or needs entity collections and devtools (section 6).

1.6 API contracts, mapping and recovery

  • Source of truth: each service's OpenAPI document (the framework already serves Swagger). CI generates TypeScript types into shared/api-types; adapters map DTOs to domain models. Components never see DTOs.
  • The envelope is typed once in platform/http: Envelope<T> = { data?: T; errors?: { code: string }[]; correlationId?: string }. One function turns an HTTP response into a result: ok, refused (202 with business codes), invalid (400 with field codes), unauthenticated, forbidden, conflict, unavailable.
  • Money travels as a decimal string plus an ISO 4217 code (or integer minor units — DECISION with the backend); never as a JavaScript float. Dates travel as ISO 8601 with offset for instants, and YYYY-MM-DD for business dates.
  • Versions: every mutable entity carries its row version; every update sends it back (D5).
  • Idempotency: every non-idempotent command (create, check-in, post charge, payment) sends Idempotency-Key; the key is created when the person presses the button and reused for every retry of that same press (D6).
  • Correlation: the BFF assigns a trace id per request (W3C traceparent); the UI shows the envelope's correlation id on any error so support can find the server log.
  • Contract tests: the generated types are compiled against the adapters in CI; a breaking change in a service's OpenAPI fails the frontend build before release, not in production.

  • Transport: @microsoft/signalr 10.0 (the ASP.NET Core client). The browser connects to the BFF with its cookie; YARP proxies the WebSocket and attaches the access token server-side. The framework's existing ?access_token on /wss is then only used between BFF and hub, never by the browser.
  • Ordering: per-property sequence numbers; any gap or reconnect triggers a resync. Events are hints to refetch or patch, not the source of truth.
  • Bursts: events are queued and applied once per animation frame, deduplicated by entity id keeping the highest version. Night audit and group check-in can emit hundreds per second.
  • Concurrent edits: on a version conflict the form keeps the person's changes, shows the other person's current values side by side, and lets them re-apply. No silent overwrite.
  • Presence (later): "Maha is editing this reservation" is a convenience, not a lock; the version check remains the guard.

1.8 Tenant and property switching, permissions, entitlements and session lifecycle

Context

  • Tenant and organisation come from the session (the token's tenant_id/org_id, held by the BFF). The browser never chooses a tenant by sending an id.
  • Property is chosen in the global bar and lives in the URL. Switching navigates to the same page in the other property; property-scoped caches, real-time subscriptions and drafts for the old property are closed (drafts with unsaved changes ask first).
  • Office staff working under a support grant see a permanent banner naming the client, the grant's reason and its expiry.

Permissions and entitlements

  • The session response lists effective permission ids per property and the entitlements of the organisation and property (D2). platform/access exposes can(permission, property?) as a signal, a route guard and a structural directive.
  • The UI hides what the person cannot do and explains disabled actions ("Your role cannot post charges"). It never relies on hiding for safety: every call is checked again by the service ([RequirePermission], tenant and organisation filters).
  • A 403 with 000.4 refreshes the session once (roles may have changed) and then shows the refusal.

  • must_change_password routes to the change-password page before anything else.

1.9 Design system, responsiveness, accessibility, language, money and time

Design system

  • Tokens come straight from home(7): the locked palette, the type scale, density levels and dark-mode values. They become CSS custom properties in libs/ui/tokens; components use tokens only (a lint rule refuses raw colour literals in component styles).
  • Behaviour comes from @angular/cdk (overlay, bidi, scrolling, a11y focus management) and @angular/aria (headless WAI-ARIA patterns: listbox, combobox, menu, tabs, tree, grid). No visual component library: Material's look is not Harmony's.
  • Icons: the home(7) SVG set as an <hr-icon> component; direction icons mirror in RTL.
  • Motion: ANGULAR @angular/animations is deprecated in 22 ("Use animate.enter and animate.leave instead"); use CSS transitions with those hooks, and honour prefers-reduced-motion.

Responsive behaviour

Proven in the prototype and carried over: layout follows the container, not the window (CSS container queries on the stream and other panels); "Needs you" becomes a drawer below 1180 px instead of disappearing; below 720 px of height the work area scrolls as one page. The supported floor is 1366×768 at 125 %; 911×512 (150 %) must remain usable without horizontal scrolling.

Accessibility

  • Money: a Money value type (decimal string + currency). Display with Intl.NumberFormat(locale, { style: 'currency', currency }), which knows each currency's minor units (JOD 3, SAR 2). Arithmetic is the server's job; the client never adds money except for display totals already given by the API.
  • Instants are shown in the property's time zone, not the device's: Intl.DateTimeFormat(locale, { timeZone: property.timeZoneId }). A front desk in Amman viewed from a laptop set to Dubai shows Amman times, labelled with the zone when they differ.
  • Business date comes only from the server (property context), as YYYY-MM-DD; it is never derived from the device clock. During night audit the bar shows the business date marker, as in the prototype.
  • STANDARD The Temporal API is not Baseline yet (MDN). For date arithmetic in a property's zone (room timeline, stay lengths), use temporal-polyfill 1.0 behind shared/domain helpers, so the polyfill can be removed later without touching features.

2.2 Techniques

Rendering

  • Zoneless (default) and OnPush on every component, so only signal changes re-render.
  • computed() for every derived value; no function calls in templates that compute on each check.
  • @for always with track on a stable id (never $index for data rows).
  • Expensive pure computations (availability matrix, collision series) in the domain layer, memoised by input identity; above about 16 ms move to a Web Worker.
  • @defer (on viewport | on idle) for charts, history, rarely opened panels.

Lists, grids, timelines

  • CDK virtual scroll for long one-dimensional lists (fixed row height per density).
  • The room timeline (rooms × nights) draws on a <canvas> with a DOM layer only for focus and the selected cell; keyboard navigation and screen-reader summaries come from the DOM layer, not the canvas.
  • Server-side paging and filtering for anything over a few thousand rows; the client never downloads a whole hotel history.

Network and memory

  • Resources cancel their request when their parameters change or their owner is destroyed; feature code uses AbortSignal for anything manual.
  • Store caches are LRU-bounded (for example 20 entities per detail store, 5 list pages per query) and cleared on property switch.
  • Every subscription, interval, observer and hub handler is tied to a DestroyRef; the soak test proves it.
  • Fonts self-hosted, subsetted for Latin and Arabic, font-display: swap; icons inline SVG; images (guest photos, scans) loaded on demand and never cached by the service worker (none is used).

2.3 Measurement, profiling and monitoring

  • Lab: Lighthouse CI on the shell and three key routes with fixed data; Playwright performance scenarios record traces on every merge to main. Lab numbers are for regressions only; they are not user experience.
  • Field (RUM): web-vitals 6.2 attribution build sends LCP, INP and CLS with route and release to the telemetry endpoint through the BFF; dashboards at p75, segmented by device class and property.
  • Profiling: Angular DevTools profiler for change-detection hot spots; Chrome performance panel for long tasks; heap snapshots for leaks.
  • Regression checks in CI: bundle budgets fail the build; Lighthouse CI fails if LCP or CLS regress beyond a set margin; the scroll and burst scenarios fail on any long task over 50 ms.

2.4 Deployment and caching

  • Content-hashed files (main-*.js, chunks, styles) served with Cache-Control: public, max-age=31536000, immutable.
  • index.html served by the BFF with Cache-Control: no-store (it carries the per-request CSP nonce).
  • The last three releases' chunks stay on the server, so a tab opened before a deploy can still load its lazy routes (section 4.6).

3.3 Authentication, session expiry and sign-out through the BFF

  • Sign-in: full-page navigation to /bff/login?returnUrl=…; the BFF pushes the authorization request (PAR), Identity shows its own pages, the BFF exchanges the code with PKCE and private_key_jwt, and sets its cookie. returnUrl must be a relative path checked by the BFF (open-redirect).
  • Expiry: refresh happens on the BFF; when it fails, API calls return 401 and the app follows section 1.8.
  • Sign-out (this device): POST /bff/logout with the anti-forgery header; the BFF revokes the refresh token, clears its cookie and redirects through Identity's end-session endpoint. "Sign out everywhere" calls the Identity API through the BFF and bumps security_version.
  • The existing password-grant client and the React app's sessionStorage tokens are retired when the BFF is live (D15).

3.7 Negative tests (must fail safely)

  1. Change /p/GRD/ to another organisation's property code in the URL → the API refuses (403/404 by policy), the UI shows "Not available" and leaks no data, and no request carries the foreign id beyond the first refusal.
  2. Replay a captured API request from another origin without the anti-forgery header → BFF refuses.
  3. Call /api/* without the cookie → 401 envelope; with a cookie for tenant A against a tenant-B resource id → refused.
  4. Demote a user while their tab is open → next call 401 (stale security_version), UI returns to sign-in, drafts kept in memory only.
  5. Inject <img src=x onerror=…> into every text field that is later displayed (guest names, notes) → rendered as text; zero CSP or Trusted Types violations.
  6. Open /bff/login?returnUrl=https://evil.example → redirected to the app root, never off-site.
  7. Support-grant staff after the grant expires → refused on the next call; banner shows "Grant expired".
  8. A user with a permission at property A but not B → B's routes hidden and B's APIs refuse the action.

4.2 Global versus local

Local handling comes first: the component that made the call decides how to show validation, refusals and conflicts, because only it knows the field or action. The interceptor and the global handler take only what no component can handle (sign-in, outages, crashes, updates). Every error that reaches the global handler is reported; local handling of an expected code is not an error and is counted, not reported.

4.3 Safe retry rules

  1. GET/HEAD: up to 2 automatic retries with exponential backoff and jitter (0.5 s, 1.5 s), only for network errors, 502, 503, 504.
  2. Commands with an Idempotency-Key: automatic retry allowed for network errors and 503, with the same key.
  3. Commands without a key: never retried automatically.
  4. Payments: never retried; outcome queried by key (workflow D).
  5. 401 and 403 are never retried as such (401 leads to sign-in; 403 to one session refresh).

4.4 Drafts

Each form registers its model with the draft registry. Drafts survive: an error, a sign-in round trip, a language switch, an app update reload in the same tab (kept in memory and restored by route). They do not survive closing the tab, by design, because they can hold guest personal data (D12).

4.5 Correlation, privacy-safe logging and monitoring

  • Every request carries W3C traceparent; the BFF links it to the service call. The UI shows the envelope's correlation id on errors.
  • Client logs contain: error kind, code, route pattern (/p/:property/front-office/check-in, not the real codes), release, browser, correlation id. They never contain names, document numbers, card data, free text the person typed, or tokens.
  • Alerts: error rate per release, chunk-load failures, uncertain-payment count, CSP/Trusted Types reports, 401 spikes (identity problems).

4.6 Application updates and failed chunks

The BFF serves /version.json; the app checks it on focus and every 10 minutes. A new version shows a quiet "Update ready — reload when convenient" banner; it becomes blocking only when the API declares the old client incompatible (a minimum client version header). Old chunks are kept for three releases, so failures are rare; when one happens, the router error handler saves drafts and offers a reload.

7.2 Hotel scenarios that must have end-to-end tests

  1. Morning shift: sign in → choose property → "Hotel now" → assign room → check in → encode key (stub) → post payment.
  2. Two clerks edit the same reservation in two browser contexts; the second sees the conflict view and keeps their input.
  3. Property switch with an unsaved draft; drafts per property restored; no data from the first property appears.
  4. Role demoted mid-shift: next action returns to sign-in; after sign-in the draft returns and the forbidden action is explained.
  5. Network drop during check-in: banner, safe retries with the same idempotency key, no duplicate check-in.
  6. Hub disconnect and reconnect: resync happens, no stale counts remain.
  7. Night audit running: business date marker, blocked actions explained.
  8. Arabic, dark, 1366×768 at 125 % and 150 %: the prototype's layout audit, ported.

Risks

  • Backend contracts arrive later than the UI. Mitigation: build each slice against an agreed OpenAPI document and a contract-tested fake before the service exists.
  • New Angular APIs change. Aria and Signal Forms are new; resources became stable in 22.0. Mitigation: wrap them in our ui/platform libraries; re-check API status at each minor.
  • Peer ranges lag. TypeScript 7 is already out; libraries may move before Angular does. Mitigation: no overrides; upgrade only together with Angular.
  • Licence and data-residency choices (grid, telemetry, payments) can stall phases 4–5. Mitigation: decide D8, D9, D11 early.
  • Two front ends during migration. Mitigation: retire React and the password client as a phase 2 exit criterion, not later.

Objective production release gates

  1. All unit, component, integration, contract and end-to-end suites pass on the release commit; no test skipped without a linked, approved exception.
  2. Negative security suite (section 3.7) passes 100 %; DAST baseline shows no high findings; dependency scan shows no high or critical advisories without an accepted exception.
  3. CSP and Trusted Types enforced in staging for 7 days with 0 violations from the app's own code.
  4. axe: 0 serious or critical issues on the key routes; keyboard suite passes; manual screen-reader walkthrough of the release's new flows recorded.
  5. Layout audit passes at all supported viewports in Arabic and English, light and dark.
  6. Bundle budgets pass; staging RUM (or lab equivalents where RUM is not yet available) within the section 2.1 targets.
  7. 8-hour soak: heap growth within budget, no failed session transitions.
  8. Rollback drill done for this release: previous index.html restored and verified in under 5 minutes.
  9. External penetration test before the first production tenant (repo decision for Identity; extended to the web app).
