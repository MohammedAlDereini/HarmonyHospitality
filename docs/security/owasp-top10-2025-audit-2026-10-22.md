## Summary

The code that handles identity is careful: deny-by-default authorization, PAR + PKCE + private_key_jwt, server-side sessions, sid-bound logout with Clear-Site-Data, validated back-channel logout, nonce CSP with Trusted Types, Strict `__Host-` cookies, Data-Protection-sealed tickets, 256-bit one-time secrets spent atomically, rank rules on every admin door, a tenant wall from the framework, lockout, HIBP, append-only audit trail. No SQL injection, XSS, CSRF, IDOR or SSRF path was found.

The main risks are in the repository itself and at its edges:

1. Real secrets live in git: three private keys (token signing, Data Protection wrapping, BFF client assertion), the Redis CA and server keys, Redis passwords, and a personal Gmail app password. The server-day plan in docs/later.md already lists "secrets out of git, rotated, history purged"; this audit confirms it is the first thing to do.
2. Two open redirects in the BFF (the new `?lang=` redirect and the `returnUrl` filter after sign-in), both on the sign-in domain, both cheap to fix.
3. A tenant administrator can create global lookup rows that every other tenant sees.
4. A hand-written recursive CBOR walker in passkey registration can be driven into a stack overflow by a signed-in user, which ends the Identity process.
5. Production settings trust no proxy, so per-caller rate limits and the sign-in trail see the front door's address, and the SQL connection skips certificate validation. Both are already on the server-day list.

## A01:2025 Broken Access Control

### OWASP-A01-001: `?lang=` redirect reflects a protocol-relative path (open redirect)

- CWE-601 URL Redirection to Untrusted Site ("Open Redirect").
- Severity: Medium. Unauthenticated, one crafted link on the sign-in domain sends the visitor to an attacker site; a classic phishing step against hotel staff.
- Confidence: High. The path from request to `Response.Redirect` was traced; no shape check exists.
- Location: Backend/ApiGateways/Harmony.Web.Bff/Program.cs:230-234 (uncommitted B2 code), active only when `ServeStaticFiles` is on (production).

```csharp
var path = context.Request.Path;
if (!DoorPaths.IsDoor(path) && context.Request.Query.TryGetValue(PageLanguage.Query, out var wanted) && bffSettings.Languages.Contains(wanted.ToString(), StringComparer.Ordinal))
{
    PageLanguage.Remember(context, wanted.ToString());
    var rest = QueryString.Create(...);
    context.Response.Redirect(path + rest);
```

- Entry point and path: a GET to `https://<bff>//evil.example/?lang=ar` (or `/\evil.example/?lang=ar`). Kestrel keeps the request path `//evil.example/`; it is not a door, the language is valid, so the response is `Location: //evil.example/`. Browsers read a leading `//` (and `/\`) as a scheme-relative URL and leave the site. The language value is validated; the path is not.
- Mitigations checked: `DoorPaths.IsDoor` only excludes BFF doors; `AllowedHosts` does not apply to the path; ASP.NET Core rejects CR/LF in `Location` so this is a redirect, not response splitting.
- Fix: redirect only to a path that is local by the framework's rule, e.g. build the target from `context.Request.PathBase + path` and refuse (or fall back to `/`) when `path.Value` starts with `//` or `/\`; simplest is to reuse the same local-path check proposed in A01-002, or call `Microsoft.AspNetCore.Mvc.Infrastructure`'s `IUrlHelper.IsLocalUrl` equivalent logic (`url[0]=='/' && url.Length>1 && url[1] != '/' && url[1] != '\\'`).
- Manual check: `curl -sI "https://localhost:<port>//example.org/?lang=ar"` must not return `Location: //example.org/`.
- Links: https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/ · https://cwe.mitre.org/data/definitions/601.html · https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html

### OWASP-A01-002: `LocalPathOnly` accepts `/\host` (open redirect after a real sign-in)

- CWE-601 URL Redirection to Untrusted Site ("Open Redirect").
- Severity: Medium. The victim completes a genuine sign-in and is then sent to an attacker site, which makes the follow-up phishing page very credible.
- Confidence: High. The filter is the only guard; the OIDC remote handler redirects to the stored `RedirectUri` without further checks.
- Location: Backend/ApiGateways/Harmony.Web.Bff/Program.cs:460-463, used at Program.cs:321.

```csharp
static string LocalPathOnly(string? returnUrl)
    => !string.IsNullOrEmpty(returnUrl) && returnUrl.StartsWith('/') && !returnUrl.StartsWith("//", StringComparison.Ordinal) && !returnUrl.Contains(':')
        ? returnUrl : "/";
```

- Entry point and path: `GET /bff/login?returnUrl=/\evil.example` passes the filter (starts with `/`, not `//`, no `:`), is stored in `AuthenticationProperties.RedirectUri`, survives the round trip to Identity, and after `/signin-oidc` the handler issues `Location: /\evil.example`. Per the WHATWG URL parser, browsers treat `\` as `/` in special schemes, so `/\evil.example` resolves to `https://evil.example/`. This is exactly why ASP.NET Core's own `IsLocalUrl` rejects a second character of `\`.
- Mitigations checked: no other validation between `/bff/login` and the post-callback redirect; the `returnUrl` is attacker-controlled.
- Fix: reject `\` as the second character and any control characters (`url.Length == 1 || (url[1] != '/' && url[1] != '\\')` and `!url.Any(char.IsControl)`); mirror the rule in the frontend's `goSignIn` guard, which today also lets `/\` through.
- Manual check: after sign-in through `/bff/login?returnUrl=/\example.org`, the final `Location` must be `/`.
- Links: https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/ · https://cwe.mitre.org/data/definitions/601.html · https://url.spec.whatwg.org/#path-state

### OWASP-A01-003: a tenant administrator can create global lookup categories and values

- CWE-862 Missing Authorization.
- Severity: Medium. Any hotel with the `ManageLookups` permission can write rows that every other hotel sees in its lists (cross-tenant write); edits and deletes stay with the creating tenant, so the other tenants cannot remove them.
- Confidence: High. Permission scope, command binding and repository visibility were all read.
- Location:
  - Backend/Services/Identity/Harmony.Identity.Domain/Entities/Aggregates/PermissionModule/PermissionCatalogue.cs:20: `ManageLookups` is declared with `PermissionScope.Tenant`.
  - Backend/Services/Identity/Harmony.Identity.Handler/Commands/LookupModule/Categories/Create/CreateLookupCategoryCommand.cs:9: `public bool IsGlobal { get; set; }` bound from the request body.
  - CreateLookupCategoryCommandHandler.cs:25-26: `command.IsGlobal ? LookupCategory.NewGlobal(...)`.
  - CreateLookupValueCommandHandler.cs:28 and 43-44: a global value only requires the category to be global.
  - Backend/Services/Identity/Harmony.Identity.Infrastructure/Repositories/LookupCategoryRepository.cs:42-49: `Visible()` = `!IsDeleted && (TenantId == tenantId || IsGlobal)`.
- Entry point and path: `POST /api/LookupCategory` with `{"isGlobal": true, ...}` by a hotel user holding `ManageLookups` → handler creates a global category → `POST /api/LookupValue` with `isGlobal: true` under it → rows appear in every tenant's `Visible()` query.
- Mitigations checked: `RequirePermission(ManageLookups)` is present on the controller but the permission is tenant-scoped; no `CallerIsPlatform` check guards the global flag (the Tenant and Property platform doors do have one).
- Impact: data poisoning of shared drop-downs across hotels (wrong or offensive values, confusing duplicates), and a tenant can occupy global names.
- Fix: in both create handlers refuse `IsGlobal` unless the caller is the platform tenant (same `CallerIsPlatform` check used by the Tenant commands), or split the capability into a platform-scoped `ManageGlobalLookups` permission. Mass assignment of `IsGlobal` is the vehicle, but the root cause is the missing authorization, so it is reported once here (A08 is not duplicated).
- Links: https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/ · https://cwe.mitre.org/data/definitions/862.html · https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html

Checked and not found in A01: IDOR on accounts, roles, tenants and properties (caller id always from the token, rank rules on every admin door, tenant filter from the framework on `IMultiTenantEntity`); forced browsing (fallback policy requires authentication in the BFF, `AuthorizationConventionCheck` at Identity start, every action decorated); CSRF (`x-csrf: 1` plus Origin match on `/bff` and `/api`, Strict cookies, sid proof on `/bff/logout`); path traversal (language from a validated list, docs name matched against configuration); SSRF (YARP routes fixed, docs fetch limited to configured services).

### OWASP-A02-001: passwords and license material in versioned configuration

- CWE-260 Password in Configuration File.
- Severity: Medium. These are development and infrastructure credentials; they give anyone with repository read access a working Redis login on the development stack and the development super-admin password. Severity rises to Critical if any of them is reused in a live environment.
- Confidence: High that they are committed; Medium on where they are used (deployment not visible).
- Locations (values masked, never reproduced):
  - Backend/Services/Identity/Harmony.Identity.Api/applicationSettings.Development.json: Redis password (32 random characters), SuperAdmin password (20 characters), see also A07-001 for the SMTP password.
  - Backend/ApiGateways/Harmony.Web.Bff/applicationSettings.Development.json: Redis password (32 random characters).
  - infra/redis/users.acl: the same per-service passwords in `>` plaintext form (`identity`, `webbff`, `reservations`, `folio`, `housekeeping`).
  - secrets/redis-identity.txt, secrets/redis-webbff.txt, secrets/identity-apidocs-password.txt: 32-character random values. The Redis ones are the development ACL passwords (the same values sit in infra/redis/users.acl and inline in the Development settings; the harness reads them from these files); the API-docs one is the Basic password the BFF docs page reads.
  - Duende `LicenseKey` (a 2185-character JWT carrying the licensee's name and a personal e-mail) in all four Identity settings files: `[SECRET MASKED]`. Not a credential, but licensed material that should not sit in a repository that others may be given.
  - Production/QA/UAT Identity settings: Redis password is an 18-character placeholder; SuperAdmin password empty (the seed refuses to start, which is fail-closed and good); UAT SuperAdmin e-mail is a personal Hotmail address.

This is item 1 of the server-day list in docs/later.md L1b.
- Links: https://owasp.org/Top10/2025/A02_2025-Security_Misconfiguration/ · https://cwe.mitre.org/data/definitions/260.html · https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html

### OWASP-A02-002: production settings trust no proxy, so per-caller controls key on the front door's address

- CWE: none of the A02-mapped CWEs describes this precisely; reported as an active configuration gap.
- Severity: Medium. Behind a reverse proxy, every caller shares one address: one attacker exhausts the sign-in, forgot-password and reset buckets for all users (denial of sign-in), lockout-by-IP cannot single out anyone, and the sign-in history and security trail record the proxy's address, which weakens incident response.
- Confidence: Medium. The settings are committed and read; the deployed topology (direct exposure versus edge proxy) is not visible.
- Location: `TrustedProxyAddresses` absent from Backend/ApiGateways/Harmony.Web.Bff/applicationSettings.json; `TrustedProxies.Addresses` present only in Backend/Services/Identity/Harmony.Identity.Api/applicationSettings.Development.json. Rate-limit partitions use `RemoteIpAddress` (Program.cs:136; Harmony.Identity.Infrastructure/RateLimiting/RateLimitPolicies.cs:51-63). Forwarded headers are only honoured when a trusted list exists (correct: an empty list trusts nobody rather than everybody).
- Fix: on the server day, list the edge's addresses (or network) in both apps' production settings, keep `ForwardLimit` bounded to the number of hops, and verify with a request carrying a forged `X-Forwarded-For` that the logged address is the real client only when it came through the edge. Already item 2 of docs/later.md L1b.
- Links: https://owasp.org/Top10/2025/A02_2025-Security_Misconfiguration/ · https://learn.microsoft.com/aspnet/core/host-and-deploy/proxy-load-balancer

### Informational

- `UseHsts()` is called by both apps outside Development (BFF Program.cs:209, Identity Program.cs:100) while docs/later.md L2 says the edge sends HSTS and the apps do not. Harmless (two identical headers), but decide one owner so `preload` and `max-age` do not drift.
- Backend/Services/Identity/Harmony.Identity.Api/Harmony.Identity.Api.http still targets the template's `weatherforecast` route (A02.9 leftover). Delete it.
- Rate-limit counters are in-memory per instance (Identity and BFF): with N instances every limit is N times larger. Documented in docs/later.md; fine for one instance.
- The BFF production Redis password could not be located (empty in the settings file, and the `secrets/redis-webbff.txt` value matches nothing). `[MANUAL VERIFICATION REQUIRED]` that production injects it; Redis ACL rejects an empty password, so the failure mode is fail-closed.

Checked and not found: debug switches in production (developer exception page and Swagger wall are Development-only; the BFF blocks `/api/{service}/swagger` and `/healthchecks`); cookie flags (`__Host-`, Secure, HttpOnly, SameSite Strict/Lax as intended); CORS (none, on purpose); XML parsing (none); directory listing (none); security headers (nonce CSP, `default-src 'none'` on doors, XFO DENY, no-referrer, COOP/CORP, Permissions-Policy, nosniff, `no-store` on `/api` and sign-in pages).

## A04:2025 Cryptographic Failures

### OWASP-A04-001: private keys committed to the repository

- CWE-321 Use of Hard-coded Cryptographic Key.
- Severity: High. Whoever can read the repository holds (a) the RSA key that signs every Harmony token, (b) the certificate and key that wrap the Data Protection key ring (cookies, tickets, authenticator secrets, recovery codes), (c) the EC key with which the BFF proves itself to Identity, and (d) the Redis CA and server keys. If these files are the ones mounted in a live environment, tokens, cookies and client assertions can be forged (Critical). As committed development material the direct impact is on the development stack only, but the production settings point at `/run/secrets/` files with exactly these names, which invites copying them.
- Confidence: High that they are committed (git ls-files); Medium on live reuse.
- Location (tracked in git): secrets/identity-signing-key.pem (`-----BEGIN RSA PRIVATE KEY-----`, 2048-bit, `[SECRET MASKED]`), secrets/identity-dataprotection.pem (certificate + private key), secrets/web-bff-client-key.pem (EC private key), infra/redis/tls/ca.key, infra/redis/tls/redis.key. The comment at Harmony.Identity.Infrastructure/Signing/RsaSigningKeyProvider.cs:10 ("every environment runs from a real key file") shows the intent; the file itself still sits in git.
- Fix: generate fresh keys per environment outside the repository (Development: user-secrets or a local, ignored folder; servers: `/run/secrets` from the host's secret store), add `secrets/`, `*.pem`, `*.key` to `.gitignore`, rotate the live keys, and purge history. Consider turning on Duende automatic key management (RSA ring in the operational store, encrypted with Data Protection) to get rotation without files. The token key is the most urgent because old tokens signed with the exposed key remain valid until they expire.
- Links: https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/ · https://cwe.mitre.org/data/definitions/321.html · https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html

### Informational

- infra/redis: the plaintext port 6379 is published next to TLS 6380 (docker-compose.yml:7-8), and `tls-auth-clients no` (redis.conf:11). Development stack only; CWE-319 would apply if the same compose file reached a shared network. Keep 6379 unpublished and require client certificates when it does.
- Key rotation is manual (Duende key management off, own RSA ring from a file). Plan a rotation calendar or enable automatic management.

Checked and found sound: RS256 with a 2048-bit key, ES256 client assertions (60 s, GUIDv7 jti), PKCE, Data Protection keys in SQL (Identity) and Redis (BFF) wrapped by a certificate, authenticator keys and recovery codes encrypted at rest, link secrets stored as SHA-256, 256-bit random secrets from `RandomNumberGenerator`, constant-time comparisons, ASP.NET Core Identity password hashing (PBKDF2, default iterations), HTTPS metadata required, `RequireHttpsMetadata` on.

## A06:2025 Insecure Design

### OWASP-A06-001: token-refresh lock may be released by a waiter that never acquired it

- CWE-362 Concurrent Execution using Shared Resource with Improper Synchronization (Race Condition).
- Severity: Low. The worst outcome is a double spend of a one-time refresh token, after which Duende revokes the family and that one user is signed out everywhere (self-inflicted session loss, no cross-user impact).
- Confidence: Medium. The code path is clear; whether `UnlockAsync` checks ownership lives in Harmony.Core.Cache, which is out of scope.
- Location: Backend/ApiGateways/Harmony.Web.Bff/Authentication/CookieOidcRefresher.cs:82-93. A request that fails to acquire the lock waits up to 20 × 250 ms, then reaches the `finally`-style `UnlockAsync(lockKey)` at line 93 whether or not it ever held the lock; if the cache lock has no owner token, this releases the winner's lock while the winner is still mid-refresh, and a third request can start a second refresh with the same token.
- Fix: unlock only when `AcquireLockAsync` returned true for this request (track an `acquired` flag), and prefer a lock primitive that carries an owner token so a foreign unlock is a no-op.
- Links: https://owasp.org/Top10/2025/A06_2025-Insecure_Design/ · https://cwe.mitre.org/data/definitions/362.html

### Informational

- Password-reset and invitation links use the default Data Protection token lifetime (24 hours). Reset links are a recovery path (A06.3); a shorter life (1 to 2 hours) narrows the window on a leaked mailbox without hurting invitations, which can keep 24 hours.
- Two-step sign-in (TOTP) can be set up and enabled with the session alone; disabling it needs the password, and passkeys need a fresh proof of identity. Binding a new authenticator is the step NIST SP 800-63B asks to re-authenticate for; reported under A07 as a design lead.

Checked and found sound: tenant isolation (framework query filter on every `IMultiTenantEntity`, platform doors guarded by `CallerIsPlatform`); recovery (forgot-password always answers 200, per-account 60 s throttle, same codes for unknown mail and bad token); concurrency on one-time secrets (spend-first atomic Redis operations for MFA challenges, e-mail links, passkey challenges, identity confirmation); no file upload; bot protection is rate limiting plus lockout (no CAPTCHA, by design, acceptable for a staff application).

## A07:2025 Authentication Failures

### OWASP-A07-001: a personal Gmail app password is committed in Development settings

- CWE-798 Use of Hard-coded Credentials.
- Severity: High. A Google app password is a full credential for that mailbox over IMAP/SMTP, not just "send mail": anyone with repository access can read and send as the owner's personal account. It is a real third-party credential, not a placeholder.
- Confidence: High. Key names and value shape were inspected (`SmtpHost` = smtp.gmail.com, `SmtpUserName` = a personal address, `SmtpPassword` = 19 characters in the Google app-password form). Value never printed: `[SECRET MASKED]`.
- Location: Backend/Services/Identity/Harmony.Identity.Api/applicationSettings.Development.json (`Mail` section). The same file is copied into bin/ on every build.
- Fix: revoke the app password in the Google account now, move SMTP settings to user-secrets or a local ignored file, use a dedicated non-personal sender (or a local SMTP sink such as smtp4dev in Development), and purge history as part of A02-001 / A04-001.
- Links: https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/ · https://cwe.mitre.org/data/definitions/798.html

### OWASP-A07-002: SQL Server certificate validation disabled in production, QA and UAT

- CWE-295 Improper Certificate Validation.
- Severity: Low as committed (the server is `localhost` with Windows authentication, so a man-in-the-middle needs a foothold on the host); Medium the day SQL moves to another machine.
- Confidence: High that the flag is in the committed files; the live connection string could differ.
- Location: `ConnectionStrings:Default` in Backend/Services/Identity/Harmony.Identity.Api/applicationSettings.json, applicationSettings.Qa.json and applicationSettings.Uat.json: `...;Trusted_Connection=True;TrustServerCertificate=True` (no credentials inside).
- Fix: install a certificate the host trusts on SQL Server and set `Encrypt=True;TrustServerCertificate=False` (docs/later.md L1b item 3).
- Links: https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/ · https://cwe.mitre.org/data/definitions/295.html · https://learn.microsoft.com/sql/relational-databases/security/networking/tds-8

### OWASP-A07-003: sign-in responses distinguish account states (enumeration lead)

- CWE: none assigned (per the A07.3 rule, enumeration is a lead unless a concrete authentication weakness follows).
- Severity: Low. Rate limiting (sign-in bucket) and lockout bound the probing rate; the leak is which e-mails exist, which are suspended and which tenants are suspended.
- Confidence: High (messages read).
- Location: Backend/Services/Identity/Harmony.Identity.Api/Pages/Account/Login.cshtml.cs:179-182 returns four different texts for `AccountNotActive`, `TenantNotActive`, `LockedOut` and `TenantRequired` versus the generic invalid-credentials text. Backend/Services/Identity/Harmony.Identity.Infrastructure/IdentityServer/SignIn/PasswordCheck.cs:76-79 returns before any hash computation when the name is unknown, so timing also differs (unknown name is faster than wrong password).
- Fix: one generic message for everything except lockout (lockout may stay explicit, since the attacker already knows the name), and run a dummy `PasswordHasher.VerifyHashedPassword` against a fixed hash when the user is unknown so both paths cost the same.
- Links: https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/ · https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-responses

### OWASP-A07-004: enabling two-step sign-in needs no fresh proof of identity

- CWE: none assigned (design lead).
- Severity: Low. A hijacked session (hours old) can enrol an attacker's authenticator and take the recovery codes; the owner then cannot sign in without an administrator. Disable needs the password and passkeys need the 5-minute identity confirmation, so this is the one inconsistent door.
- Confidence: High.
- Location: Backend/Services/Identity/Harmony.Identity.Handler/Commands/UserAccountModule/TwoFactor/SetupTwoFactorCommandHandler.cs and EnableTwoFactorCommandHandler.cs (session + code only).
- Fix: require the same identity confirmation used by `AddPasskey` before `SetupTwoFactor`, and send a security mail on enrolment (the device-mail path already exists).
- Links: https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/ · https://pages.nist.gov/800-63-3/sp800-63b.html#sec6

### Informational

- The e-mail sign-in page completes a sign-in on GET (Pages/Account/EmailSignIn.cshtml.cs:45) without a rate-limit policy. The link carries a 256-bit secret, is bound to a cookie and is spent once, so guessing is not practical; a policy would only add defence in depth.
- Duende's jti replay cache is in memory (docs/later.md L4): with two Identity instances a client assertion could be replayed once against the other instance within its 60-second life. Documented; fine for one instance.
- Fail-open behaviours are reported under A10.

Checked and found sound: lockout 5 tries / 5 minutes; password rules 12+ characters with a symbol, context-word and HIBP checks; PAR required, PKCE, `private_key_jwt` with audience validation; one-time sliding refresh tokens with absolute cap; server-side sessions; `IsActiveAsync` checks user, tenant and `security_version` on every issuance; `SecurityVersion` revocation; sid-bound logout and Clear-Site-Data; back-channel logout JWT fully validated with 10-minute jti replay guard; device cookie with hashed key and new-device mail; `__Host-` cookies, Strict for the sensitive ones; id_token validated on refresh with sub match; OIDC `MapInboundClaims=false`.

## A09:2025 Security Logging and Alerting Failures

### OWASP-A09-001: CSP violation reports write attacker-controlled strings to the log

- CWE-117 Improper Output Neutralization for Logs.
- Severity: Low. The report door is anonymous (it must be), so anyone can submit a report; with a plain-text log sink, new-line characters in `disposition`, `effective-directive` or a non-URI `blocked-uri` forge log lines or hide real violations. With a structured JSON sink the values are escaped and the impact is only noise.
- Confidence: Medium. The input path is read; the sink (Harmony.Core.Logging) is out of scope.
- Location: Backend/ApiGateways/Harmony.Web.Bff/Security/CspViolationReports.cs:90-96. Size (8 KB), content-type and 60-per-minute-per-IP limits are in place; `PathOnly` returns non-URI strings verbatim; the `sample` field is cut to 40 characters.
- Fix: whitelist `disposition` (`enforce`/`report`) and `effective-directive` against the known directive names, strip control characters from every logged value, and keep the structured sink.
- Links: https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/ · https://cwe.mitre.org/data/definitions/117.html · https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html

### Informational

- The back-channel logout handler logs the `sid` at Information level. A sid alone cannot end a session (the logout door also needs the session cookie), so this is not CWE-532 material; still, log it at Debug or hash it.
- Alerting and log centralisation are not visible in the repository (no sink or SIEM configuration): not assessable.

Checked and found sound: `SecurityAuditEvents` is append-only with capped detail; sign-ins, failures, lockouts, second-factor refusals, password and passkey changes and device events are recorded with the user id; no password, token or secret is written to a log in the code read.

## A10:2025 Mishandling of Exceptional Conditions

### OWASP-A10-001: recursive CBOR walker in passkey naming can overflow the stack and end the Identity process

- CWE-248 Uncaught Exception (A10-mapped label; the precise weakness is CWE-674 Uncontrolled Recursion). A .NET `StackOverflowException` cannot be caught: the process terminates.
- Severity: High. One request from any signed-in, identity-confirmed user takes the identity provider down for every tenant; it can be repeated after each restart (the passkey door allows 30 sends then 10 per minute).
- Confidence: Medium. The reachable path and the absence of a depth limit are traced; not executed. The remaining unknown is whether ASP.NET Core's own attestation parser, which runs first, rejects deeply nested attestation statements (its reader is iterative and the attestation statement is not verified by default, so it is expected to pass).
- Location: Backend/Services/Identity/Harmony.Identity.Infrastructure/Passkeys/PasskeyMakers.cs:71-99 (`AuthDataOf` walks the top-level map) and :132-155 (`Skip` recurses into arrays, maps and tags for every value that is not `authData`). Reached from Backend/Services/Identity/Harmony.Identity.Handler/Commands/UserAccountModule/Passkeys/AddPasskeyCommandHandler.cs:117 (`UserPasskey.NameOf(... PasskeyMakers.NameOf(attestationObject))`) after `PerformAttestationAsync` at line 90 succeeded. The request body is capped at 64 KB (AddPasskeyCommand.cs:10).
- Entry point and path: `POST /api/UserAccount/passkeys` with a credential JSON whose attestation object has a valid `authData` but an `attStmt` (or any extra key) made of tens of thousands of nested one-element arrays (`0x81 0x81 …`, about 45 000 levels fit in 64 KB). Each level is one `Skip` frame; the default 1 MB thread stack is exhausted long before the end.
- Fix: replace the hand-written walker with `System.Formats.Cbor.CborReader` (iterative, with `ReadStartArray`/`SkipValue`), or add a depth counter to `Skip` that throws an ordinary exception past, say, 16 levels, and read the AAGUID from the already-parsed `authData` that `PerformAttestationAsync` returns instead of re-parsing the attestation object.
- Manual check (only in a disposable environment): build such a credential JSON and submit it once; the service must answer 400, not die.
- Links: https://owasp.org/Top10/2025/A10_2025-Mishandling_of_Exceptional_Conditions/ · https://cwe.mitre.org/data/definitions/248.html · https://cwe.mitre.org/data/definitions/674.html

### OWASP-A10-002: two checks fail open when their backing store is unavailable (accepted by decision)

- CWE-636 Not Failing Securely ("Failing Open").
- Severity: Low. Both are deliberate availability trade-offs with a warning in the log; they only matter while Redis or the HIBP service is down.
- Confidence: High.
- Location: Backend/Services/Identity/Harmony.Identity.Infrastructure/IdentityServer/SignIn/SecondFactorCheck.cs:181-182 (used-code store unreachable → the TOTP code is accepted without replay protection for that check); Backend/Services/Identity/Harmony.Identity.Infrastructure/Passwords/LeakedPasswordValidator.cs:61 (HIBP unreachable → password accepted; decision of 2026-10-07).
- Fix: none required if the decision stands. If the replay guard should fail closed, return `Refused` on a store error and let the user retry; the HIBP case could be re-checked asynchronously on next sign-in.
- Links: https://owasp.org/Top10/2025/A10_2025-Mishandling_of_Exceptional_Conditions/ · https://cwe.mitre.org/data/definitions/636.html

Checked and found sound: Identity's Error page shows detail only in Development; the BFF has no custom exception page (empty 500 outside Development, developer page inside); `OnRemoteFailure` logs and sends home; cache reads fail closed; the super-admin seed refuses to start without a strong password; time-zone ids are validated at creation so `FindSystemTimeZoneById` cannot throw later; every `try/catch` read either rethrows, logs with a decision, or fails closed.
