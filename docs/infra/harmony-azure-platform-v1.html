1The honest answer

You asked for an app that never goes down and a setup that is 100% complete. No cloud sells that, and Microsoft's own guidance says so. Here is what we can promise and prove instead.

Never down is not on sale

Microsoft publishes availability promises (SLAs) for each service, and none is 100%. Its Well-Architected guidance says a system's availability is the product of its parts: every service you add lowers the ceiling. For targets of 99.99% and above it recommends at least three regions. Anyone who promises "never down" is selling a feeling, not a design.

What this design promises

One server dies

Nobody notices. Every part runs as at least two copies; Azure replaces the dead one.

One data centre dies

Nobody notices. App, database, cache and registry are spread over the three zones in UAE North. The database loses no committed data.

A bad release ships

Traffic goes back to the previous version in seconds. A new version gets traffic only after its smoke test passes.

The whole region dies

Harmony restarts in the second region under a written, rehearsed plan. Some recent seconds of data may be lost (the RPO), and users sign in again.

How a request travels

  1. The browser reaches Front Door at the nearest Microsoft edge. TLS ends there; the WAF checks the request.
  2. Front Door forwards it over Private Link to the Container Apps environment. The environment has no public address.
  3. The environment's ingress picks the app (web BFF, console BFF or Identity) by host name and a healthy copy in any zone.
  4. The BFF reads the session from Redis and calls Identity or a service on the internal network. Every data service is reached through a private endpoint.

Three public host names, three Front Door routes

Host (example)Goes toWhy public
app.harmony…web BFFThe hotel staff app and its API.
console.harmony…console BFFThe platform team's console (B9). Can also be limited by IP at the WAF.
id.harmony…IdentityThe browser must reach the sign-in pages and /connect/* directly; that is how OpenID Connect works.

Future PMS services (reservations, front desk, housekeeping, billing) get internal ingress only. The browser never calls them directly; it calls the BFF, which already proxies with YARP.

Two limits that shape later features
  • WebSockets through Front Door: idle connections close after 5 minutes, any connection after at most 2 hours, and one Front Door profile carries at most 3,000 concurrent WebSocket connections worldwide. Live front-desk updates for many hotels can hit that. Decide the live-update path before building it (A17).
  • Slow requests: Front Door waits 30 seconds for the origin by default, 240 at most. Long reports and exports must run as background jobs that the page polls, not as one long request.

7Multitenancy

Harmony's model stays: one shared database, every row carries its hotel's tenant id, and the platform tenant (us) sits outside every hotel. Azure adds a second lock and a way to grow by country.

Keep: shared database, tenant filter

HAVE MultiTenancyOptions.SharedDatabase with EF query filters. MS Microsoft lists this as the shared (pooled) model: the cheapest per hotel and the simplest to run, with noisy neighbours as its known risk.

Add: Row-Level Security as a second lock DECIDE A13

MS Microsoft recommends SQL Row-Level Security for multitenant databases. The app sets the tenant in SESSION_CONTEXT when it opens a connection; SQL itself then refuses another hotel's rows, even if a query forgets its filter. The platform tenant and the background readers that must see every hotel use a separate, audited database principal.

Grow by stamps

MS Microsoft's Deployment Stamps pattern: a stamp is one complete copy (Container Apps environment, SQL, Redis, Key Vault) serving a group of hotels. Start with one stamp in UAE North. Add a stamp when a country requires its data at home, or when a large chain needs its own.

A tenant catalogue in the platform database records which stamp holds which hotel. Front Door routes by host name. The same Bicep deploys every stamp.

Measure per hotel

MS For SaaS, Microsoft says to measure availability per customer. Tenant id is a telemetry dimension (an id, never a name or personal data), so the SLO report shows each hotel's own minutes.

Data residency is a legal question first (A3)

Microsoft's region list (checked 23 October) shows three Middle East regions with three zones: UAE North, Qatar Central and Israel Central. UAE Central is restricted and has no zones. No Saudi Arabia region appears in that list. If Saudi hotels must keep guest data in the Kingdom, that needs a lawyer's answer before the first Saudi contract, and later a stamp in a Saudi region once one exists. Re-check the list when deciding.

9Security and network

No public door except Front Door, no passwords between Azure services, no person with standing admin rights.

Network

  • Container Apps environment: internal only, public access off, own VNet (a /23 subnet for the environment, a separate /24 for private endpoints, as Microsoft's Front Door guide suggests).
  • SQL, Redis, Key Vault, Storage and ACR: private endpoints, public network access off.
  • Front Door Premium WAF: Microsoft's managed rule set and bot rules, in detection first, then prevention; rate rules per path (sign-in, password reset) until G3 lands.
  • Outbound: a NAT gateway gives one fixed address if hotels or partners must allow-list us (A14).

Identities

  • One user-assigned managed identity per app; it pulls images, reads its Key Vault secrets and signs in to SQL. Nothing else.
  • SQL: Entra-only authentication; the app identity gets read and write on data, not schema.
  • People: Entra Privileged Identity Management, no standing Owner, two break-glass accounts kept offline.
  • CI: GitHub signs in with OpenID Connect to a federated identity. No client secret anywhere.

Secrets and keys

  • Key Vault in RBAC mode with soft delete and purge protection. Only the app identities read secrets; only CI writes them.
  • Token signing keys, both key-ring certificates and the BFF's client key live in Key Vault and arrive as mounted files.
  • SEC Before any of this goes live, the secrets the 22 October audit found committed are rotated and removed from the repository (later.md L1b). The parked audit items stay parked until you say so.

Guard rails

  • Azure Policy: only the chosen regions; no public network access on data services; diagnostic logs on.
  • Defender for Cloud posture checks (free); Defender for Containers and for SQL (paid, A15).
  • Container Apps built-in roles that can list secrets are not handed out; Microsoft warns several include listSecrets.

11Observability

See a problem before a hotel calls, and know which hotel it hits.

  • One pipe: logs, traces and metrics through OpenTelemetry to Application Insights and Log Analytics (A10). ILogger stays the logging API; the Elasticsearch sink goes.
  • What we watch (SLIs): sign-in success rate, front-desk API success rate and 95th-percentile latency, per hotel; Front Door health-probe results per origin; SQL and Redis failovers.
  • Outside-in checks: Application Insights availability tests hit the sign-in page and a health page from several locations every few minutes.
  • Alerts: on burning the monthly error budget too fast, not on single errors. Someone must be on call to receive them (A18).
  • Cost control: log ingestion in UAE North is $3.29 per GB (retail, 23 October). Verbose logs are sampled; Microsoft's distro samples logs along with traces by default.
  • Never in telemetry: guest names, documents, card data or tokens. Tenant id and request id only.
